# 🛡️ AI Risk Manager — Fraud-Spike Detection for Merchants

A **defense-only** machine learning system that detects unusual spikes in potentially
fraudulent transactions for Indian merchants and helps a human risk/fraud team
investigate them. The system **never blocks, automates, or takes offensive action** —
every alert is a lead for a human analyst, with explainability and defensive
recommendations attached.

Built for the hackathon judging criterion:
> "Build a working detector, verifier or auto-responder for one class of loss, with
> measured precision and recall on a held-out test set."

---

## 1. Problem Statement

Merchants processing digital payments (UPI, cards, net banking, wallets) are exposed
to fraud that often arrives in **bursts** — a compromised device, a probing/testing
attack, or a sudden wave of high-value transactions — rather than as isolated events.
Manually monitoring thousands of transactions per merchant per day is infeasible.
Risk teams need a system that:

1. Scores individual transactions for fraud likelihood,
2. Detects when a merchant's *suspicious transaction volume* suddenly spikes above
   its own historical baseline, and
3. Gives an analyst enough context (why it was flagged, what to check, what to do)
   to investigate quickly — without ever taking automated action itself.

## 2. Solution

An end-to-end pipeline: synthetic data generation → leakage-safe feature engineering
→ a supervised Random Forest classifier → statistical spike detection on top of the
model's flags → a Streamlit dashboard for monitoring, investigation, and transparent
model reporting.

## 4. Dataset

Fully **synthetic**, generated by `data/generate_dataset.py` — no real transaction
or customer data is used anywhere.

- **126,358 transactions** over 60 days across 60 merchants (Indian cities: Mumbai,
  Delhi, Bengaluru, Hyderabad, Chennai, Kolkata, Pune, Ahmedabad, Jaipur, Lucknow,
  Surat, Nagpur, Indore, Kochi, Chandigarh).
- **Fields:** `transaction_id`, `timestamp`, `merchant_id`, `amount`,
  `payment_method`, `location`, `device_id`, `customer_id`, `transaction_status`,
  `fraud_label`.
- **~2.0% fraud rate** (2,567 fraud transactions), reflecting realistic class
  imbalance rather than an artificially balanced dataset.
- **5 fraud patterns** embedded: high-value outliers, device bursts (many rapid
  transactions from one device), geographic anomalies, failed-transaction/card
  "probing" bursts, and **14 deliberate merchant-level fraud spikes** (25–90 fraud
  transactions concentrated on a single merchant/day) used to validate the
  spike-detection logic.

## 5. ML Methodology

### Algorithm: Random Forest Classifier
`scikit-learn` `RandomForestClassifier` (300 trees, max depth 12, `class_weight="balanced"`).

Why this model:
- Captures **non-linear feature interactions** (e.g., high amount **and**
  unfamiliar device **and** odd hour is a much stronger signal than any single
  feature) without manual interaction terms.
- No feature scaling required, simplifying the pipeline given a mix of counts,
  ratios, and z-scores.
- Produces **class-conditional probabilities**, allowing a tunable decision
  threshold rather than a fixed 0.5 cutoff — important under heavy class imbalance.
- `feature_importances_` give a straightforward (if approximate) explainability
  layer for the alert-investigation view.
- Class imbalance (~2% fraud) is handled via `class_weight="balanced"`, not
  oversampling, to avoid duplicating rows across the train/val/test boundary.

Isolation Forest (unsupervised) was considered and is noted as a good
complementary option when fraud labels aren't available in production, but since
labels exist here, the supervised approach gives materially better precision/recall.

### Feature Engineering (`ml/features.py`)
All rolling/aggregate features are computed using only **backward-looking**
information (expanding means, trailing rolling windows) relative to each
transaction's timestamp — never future transactions — to prevent leakage:

| Feature | Description |
|---|---|
| `amount_zscore_vs_merchant` | How unusual this amount is vs. the merchant's running average |
| `merchant_txn_count_60min` / `_24h` | Transaction volume for this merchant in trailing windows (burst detection) |
| `device_txn_count_60min` | Transactions from this device in the trailing 60 minutes (device burst/card testing) |
| `merchant_failed_rate_24h` | Merchant's failed-transaction rate over the trailing 24h (probing pattern) |
| `merchant_spike_ratio` | Today's volume vs. this merchant's typical daily volume |
| `is_geo_anomaly` | Whether the location differs from the merchant's usual location |
| `is_night`, `is_failed`, `hour` | Time-of-day and status signals |
| `device_running_count`, `customer_running_count` | Prior transaction counts (new/rare devices & customers are riskier) |
| `pm_*` (one-hot) | Payment method |

### Train / Validation / Test Methodology
A **chronological (time-based) split** — not random — because fraud spikes are
time-clustered; a random split would leak spike information across train/test.

| Split | Days | Rows | Fraud rate |
|---|---|---|---|
| Train | 42 days | 88,565 | 2.03% |
| Validation | 9 days | 18,693 | 2.17% |
| **Test (held out)** | 9 days | 19,100 | 1.88% |

- The model is **fit only on Train**.
- The **decision threshold** is tuned **only on Validation** (target ≥75% recall,
  maximize precision at that recall) — the chosen threshold was **0.788**.
- The **Test set is touched exactly once**, after the threshold is locked in,
  purely to compute the final numbers below. No further tuning follows.

## 6. Final Held-Out Test Results (real, not fabricated)

| Metric | Value |
|---|---|
| Precision | **97.5%** |
| Recall | **65.2%** |
| F1-score | **78.1%** |
| Accuracy | 99.31% |
| False Positive Rate | **0.032%** |
| ROC-AUC | 98.99% |

**Confusion matrix (test set, n=19,100):**

| | Predicted Legitimate | Predicted Fraud |
|---|---|---|
| **Actual Legitimate** | TN = 18,735 | FP = 6 |
| **Actual Fraud** | FN = 125 | TP = 234 |

These numbers are computed directly from `models/metrics.json`, produced by
`ml/train_model.py` — they are not hand-picked or invented. At the default 0.5
threshold (also reported in `metrics.json` for comparison), recall is lower and
precision is comparable; the tuned threshold (0.788) was chosen deliberately on
validation data to push recall up while keeping false positives extremely low.

## 7. False-Positive Cost Model

The dashboard includes a **configurable** false-positive cost slider (₹ per
false positive, default ₹150) and a review-success-rate slider (fraction of
correctly flagged fraud actually recovered on review, default 90%). With the
held-out test results above (6 false positives, 234 true positives) and typical
fraud amounts in the synthetic data, the estimated fraud loss prevented vastly
exceeds the false-positive friction cost — but this is intentionally shown as a
**live, adjustable comparison** rather than a single fixed claim, since real
operational costs vary by merchant and business.

## 8. Explainability

- **Global**: Random Forest `feature_importances_`, shown as a bar chart on the
  Model & Evaluation page.
- **Per-alert**: for the highest-risk transaction in a given alert, the app shows
  the top contributing features (weighted by global importance) alongside that
  transaction's actual values, so an analyst can see *why* it was flagged.
- The dashboard explicitly states the model is **not perfectly accurate** and
  frames every alert as a lead for investigation, not a verdict.

## 9. Defensive Recommendations Only

Every alert surfaces recommendations such as: hold/review flagged transactions,
require additional verification (OTP/re-authentication), contact the merchant,
increase monitoring, escalate to a fraud team. **The system contains no logic for
bypassing fraud detection, exploiting payment systems, or taking any offensive or
automated action** — this is enforced both in the recommendation content and
tested in `tests/test_risk_scoring.py` (`test_get_recommendations_never_offensive_keywords`).

## 10. Limitations

- **Synthetic data**: realistic but simplified vs. real-world, adversarially
  evolving fraud; would need continuous retraining in production.
- **Recall is 65.2%, not 100%** — the model will miss some fraud (125 false
  negatives in the test confusion matrix). It is a lead generator, not a final
  verdict, and is presented as such throughout the UI.
- **Precision is high but not perfect** — 6 legitimate transactions were still
  flagged in the test set, incurring a friction/false-positive cost.
- **Spike detection is a simple, auditable z-score rule**, not a second learned
  model — chosen deliberately for transparency over marginal accuracy gains.
- **No real payment-network integration** — this is a decision-support demo, not
  a production fraud-blocking system.

## 11. Future Scope

- Compare against gradient-boosted trees (XGBoost/LightGBM) under the same
  time-based split.
- Add graph features (shared devices/customers across merchants) to catch
  collusion-style fraud rings.
- Replace the approximate global-importance explainability with per-transaction
  SHAP values.
- Periodic retraining with drift monitoring, since fraud patterns evolve.
- Use confirmed-fraud / false-positive analyst feedback (captured in
  `db/database.py`) to refine thresholds and the cost model over time —
  **without ever using test-set information for tuning**, to avoid leakage.

## Installation & Setup

```bash
# 1. Clone/unzip the project and enter the directory
cd ai_risk_manager

# 2. Install dependencies
pip install -r requirements.txt --break-system-packages   # or omit the flag in a venv

# 3. Generate the synthetic dataset (creates data/transactions.csv)
python3 data/generate_dataset.py

# 4. Train the model (creates models/fraud_model.joblib + models/metrics.json)
python3 -m ml.train_model

# 5. Run the tests
python3 -m pytest tests/ -v

# 6. Launch the app
streamlit run app/streamlit_app.py
```

The app will open at `http://localhost:8501`. No login is required — this is a
single-user demo (no authentication is included).

Demo data is included: after step 3–4 above, the dashboard works immediately —
no manual data upload needed.

## How the Held-Out Test Set Was Kept Separate

1. All transactions are sorted chronologically and split into Train (first 42
   days) / Validation (next 9 days) / Test (final 9 days) — see
   `ml/train_model.py::time_based_split`.
2. The model (`RandomForestClassifier`) is fit **only** on the Train rows.
3. The decision threshold that converts a probability into a "flagged" alert is
   chosen by scanning the precision-recall curve computed **only on the
   Validation set** (`choose_threshold`), targeting ≥75% recall.
4. The Test set's probabilities are computed **once**, using the frozen model
   and the threshold already fixed from validation. Test metrics are then
   reported as-is (`ml/train_model.py`, printed and saved to
   `models/metrics.json` under `"test_metrics"`) — no metric on the test set
   was used to make any further decision about the model or threshold.
5. `tests/test_model.py::test_time_based_split_no_overlap` and
   `test_saved_model_metrics_are_realistic` assert programmatically that the
   train/val/test day sets are disjoint.

## Suggested Improvements to Precision/Recall Without Data Leakage

- **More historical context per entity**: longer trailing windows (7-day,
  30-day) computed the same backward-looking way already used, to better
  separate genuinely new devices/customers from established ones.
- **Cross-validation within the training period only** (e.g., rolling-origin
  time-series CV across multiple train/validation windows within the first 51
  days) to get a more robust threshold than a single validation split, while
  still never touching the test days.
- **Gradient boosting (XGBoost/LightGBM)** with the same time-based split and
  the same validation-only threshold tuning, compared head-to-head against the
  current Random Forest.
- **Better handling of rare categorical values** (e.g., a device seen for the
  first time) via target encoding computed only from past data.
- **Cost-sensitive threshold search** directly on the false-positive-cost model
  (Section 7) instead of a fixed recall target, still fit only on validation.
